在 8 张 A800 上把 2026 年的开源模型跑起来

一台百度云百舸开发机，8 × A800-SXM4-80GB，驱动 535，没有 Docker，访问不了 HuggingFace。两天时间把 GLM-5.3-Flash（官方 FP8）、Qwen3.6-35B-A3B、Qwen3.8-27B 部署上线并完成评测。这里记录每一步的判断、踩的坑和解法，脚本都在仓库里。

核心判断：Ampere 没有 FP8，但 FP8 权重可以用 Marlin 内核以 W8A16 方式执行（权重 8 位存储、计算时解到 16 位），所以 GLM-5.3-Flash 的官方 FP8 权重是可行的；真正缺的是稀疏注意力和 KPool 索引这些 Hopper 专用内核，社区用 Triton 重写了它们。

路线 A：官方镜像加补丁，失败

第一个方案是 stozpark 的补丁链：以 vLLM 官方的 vllm/vllm-openai:glm53-flash-cu129 镜像为基底，用八个 Python 脚本做精确字符串替换，把 Hopper 专用路径换成 Triton 实现。作者 9 月 1 日在 8 × A100 上验证通过。

  • 镜像在容器里拉不下来：Docker Hub 直连被封，13 个国内镜像站全部只能拿清单、拿不到镜像层。
  • 解法：在本机用一个 400 行的纯 Python 脚本按 Registry v2 协议拉镜像层（10.5 GB，6 MB/s），边下边 rsync 到服务器（2.2 MB/s，80 分钟），服务器上按层解压成 rootfs，用 chroot 运行。
  • chroot 里 8 张卡可见、矩阵乘正常、vLLM 可导入。
  • 打补丁时第一个脚本就中断："anchor not found"。原因：vLLM 官方在 9 月 9 日把这个标签重新指向了新构建（主线 commit 385dce36），补丁是针对 8 月 25 日分支构建写的，核心文件差了 600 到 700 行。旧构建在 Docker Hub 上已无标签可寻。
教训：依赖"可变标签"的补丁方案很脆弱。社区补丁要么锁镜像摘要，要么锁源码 commit 自己编译。这个失败的镜像没有白拉，它的 vLLM 0.28 + CUDA 12.9 环境后来直接用来跑了两个 Qwen 模型。

路线 B：vllm-backport 源码编译，成功

第二个方案是 Mrzhiyao 的 glm53-a800-vllm 项目：锁定 wtdcode/vllm-backport 的源码 commit，打一个 3 万行的集成补丁，再覆盖几个在 8 × A800 上线验证过的 Triton 文件，只为 SM80 编译 vLLM 扩展。作者在和我们完全相同的硬件上验证过，单流 46.8 tok/s、1M 上下文。

  • 基础镜像 lazymio/vllm-backport:v0.11.1-sm80（8.4 GB，CUDA 13.0，Ubuntu 24.04）同样走"本机拉、rsync、解包、chroot"。它自带 nvcc。
  • 源码在本机准备（克隆、打补丁、覆盖），121 MB 同步到服务器 17 秒。
  • 编译第一次失败：镜像里没有 git，CMake 要从 GitHub 克隆 CUTLASS 等 9 个依赖。
  • 装上 git、走代理克隆：12 分钟只拉到 2 MB，放弃。
  • 9 个依赖按固定 commit 在本机克隆（2 GB），同步到服务器，通过 VLLM_CUTLASS_SRC_DIR 等 9 个环境变量指给 CMake。编译 12 分钟完成，wheel 251 MB。
  • 项目自带的 KPool 内核测试和 CUDA Graph 安全测试在 A800 上全部通过。
  • 权重 328 GB 校验完整后，TP4 × PP2 启动：加载 550 秒，KV cache 263 万 token，CUDA Graph 捕获 103 秒，单流 46.7 tok/s，和作者的数字一致。

关键技术点

用 chroot 代替 Docker

容器里没有 Docker，但有 CAP_SYS_ADMIN 和 mount 权限。把镜像层解压成目录后，绑定挂载 /proc、/sys、/dev、共享盘和缓存目录，拷入宿主机的 NVIDIA 用户态库（libcuda、libnvidia-ml 等），再用镜像自己的环境变量 chroot 进去执行 vllm serve，效果等同于 docker run --gpus all。脚本见 deploy/glm53_chroot.sh。

CUDA 前向兼容

驱动 535 只认 CUDA 12.2。CUDA 12.9 编译的 PyTorch 靠"小版本兼容"能跑，但第一次启动 Qwen 时在采样内核报 device kernel image is invalid：驱动自带的 JIT 编译器认不出新工具链生成的 PTX。解法是 NVIDIA 的前向兼容包 cuda-compat，它提供一个新版 libcuda 用户态库，和老内核模块配合工作，数据中心卡支持。镜像里都自带（/usr/local/cuda-12.9/compat），conda 环境里跑 CUDA 13 的 PyTorch 则从 NVIDIA 仓库下载 cuda-compat-13-1 解开用。

模型下载的卫生

ModelScope 命令行工具在 CDN 读超时后会跳过分片并返回成功，Qwen3.6 "下载完成"时实际有 15 个分片残缺，GLM 有 44 个。必须按远端文件清单逐个核对大小（deploy/verify_model.py）。残缺分片用 aria2c 多连接续传（-c -x 8 -s 8）比官方工具稳得多。注意 aria2 写的是稀疏文件，用 du 看不出进度，看它自己的速率日志。

压测客户端的坑

conda 环境里 vllm bench serve 一跑就报 libstdc++ 的 CXXABI 版本错误，因为 LD_LIBRARY_PATH 里先找到了系统的旧库，把 $CONDA_PREFIX/lib 加到前面即可。新版 vLLM 把参数分组隐藏，--help=all 才列全。

工具调用解析器要和模型匹配

Qwen3.8 工具调用首轮 0 分，查记录发现模型输出的是 <tool_call><function=...> 的 XML 格式，而服务配的是 hermes（JSON）解析器。换成 --tool-call-parser qwen3_xml 后 90%。思考模型做 JSON 抽取时，512 token 的预算会被思考占满，要给到 2048。
