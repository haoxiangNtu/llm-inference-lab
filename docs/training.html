从零训练一个会聊天的模型

前面几页都在用别人训练好的模型。这一页把模型的一生走一遍：训练分词器、预训练、监督微调、强化学习、评测、对话。用的是 Karpathy 的 nanochat，几千行代码覆盖全流程，原本为 8 卡单节点设计。下面每个阶段先讲它在做什么，再放这台机器上跑出来的真实数字和曲线。

d24（GPT-2 级别）正在训练中：5568 步，每步约 4.4 秒，启用 FlashAttention 3 后 MFU 约 45%，预计 2026-10-05 上午完成。完成后本页会补上 d24 的全部数字和曲线。

全流程：每个阶段让模型多会一件事

1训练分词器把文本切成 32768 种 token。模型看到的不是字，是这些编号。
2预训练在几十亿 token 的网页文本上做"猜下一个 token"。学会语言和常识，只会续写。
3监督微调 SFT喂对话数据。学会"你问我答"的格式、选择题、调用计算器。
4强化学习 RL让模型自己做题，做对的回答加强，做错的减弱。学会在特定任务上真的做对。
5评测与对话每个阶段后用固定题集量化进步，最后直接聊天看效果。

我们跑了两个规模。d12 是 12 层的小模型，和 2018 年的 GPT-1 差不多大，用来把流程走通。d24 是 24 层，目标是达到 2019 年 GPT-2 的水平。nanochat 只用"层数"一个旋钮，宽度、头数、学习率、训练步数都由它推出来。

1. 分词器

用 BPE 算法：从 256 个字节出发，反复把语料里最常相邻出现的一对合并成一个新 token，直到词表达到 32768。在 20 亿字符上训练，这台机器用时 72 秒。词表里还预留了 9 个特殊 token，比如 <|user_start|>、<|assistant_start|>、<|python_start|>，预训练时用不到，是给后面的对话格式准备的。

2. 预训练

目标只有一个：给定前面的 token，预测下一个。把语料切成 2048 token 长的片段，模型对每个位置输出一个概率分布，和真实的下一个 token 算交叉熵损失。初始损失是 ln(32768) ≈ 10.4，也就是瞎猜。

模型是标准的 Transformer 加上这几年的改进：旋转位置编码、RMSNorm、ReLU² 激活、Q 和 K 做归一化、每三层短窗口注意力配一层全局注意力。优化器分两组，矩阵参数用 Muon，嵌入用 AdamW，学习率先短暂预热、保持、后 65% 的步数线性衰减。精度是权重存 FP32、计算时转成 BF16，正好对应实验台第 5 站里"FP32 主权重 + BF16 计算"的那笔账。

8 张卡怎么一起练：每张卡跑一个进程，各读不同的数据分片，各自算梯度，然后把梯度平均后一起更新。8 张卡 × 每卡 32 条 × 2048 token，一步就是 52 万 token。大模型每卡放不下那么多，就分 4 次前向反向把梯度累积起来再更新一次。

MFU 是训练版的"内核效率"。 A800 的 BF16 峰值是 312 TFLOPS，MFU 就是实际用掉的比例。d12 第一次跑只有 27%，日志里有一行警告：FlashAttention 3 内核没加载上，回退到 PyTorch 自带实现后滑动窗口注意力只能用掩码模拟。单独测这一个算子，FA3 是 0.46 ms，掩码版是 3.69 ms。把 FA3 内核离线装好后，d24 的 MFU 到了 45%。

怎么知道预训练出来的模型有多强：CORE 指标，22 个任务的平均分，每个任务把随机水平记为 0、满分记为 1。任务都是续写或选择形式，因为这时模型还不会对话。OpenAI 2019 年的 GPT-2（15 亿参数）是 0.2565。

3. 监督微调 SFT

预训练模型只会续写。SFT 用同样的"猜下一个 token"目标，但数据换成对话，并且只在助手说的那些 token 上算损失，用户说的话和工具返回的结果不算。一条训练样本渲染成 token 后长这样：

<|bos|><|user_start|>一打鸡蛋 12 个，7 打有多少个？<|user_end|>
<|assistant_start|>一共是 <|python_start|>12*7<|python_end|><|output_start|>84<|output_end|> 84 个。<|assistant_end|>

训练数据是三种混合：46 万条日常对话（SmolTalk）教说话方式，MMLU 辅助集重复 3 遍教选择题格式，GSM8K 重复 4 遍教"遇到算术就调用计算器"。推理时引擎看到 <|python_end|> 就真的去算，把结果塞回上下文。

4. 强化学习

SFT 是"照着标准答案学"，RL 是"自己做，做对了才算"。nanochat 的做法是最朴素的 REINFORCE：每道 GSM8K 题让模型采样 16 个不同的回答，答案对的奖励为 1、错的为 0，然后把"高于这道题平均奖励"的回答的概率调高，低于平均的调低。没有 KL 约束，没有 PPO 的裁剪，这是 GRPO 一类方法的最简化版本。

d12
步数 / 时间467 步 / 1h 13m
GSM8K：SFT 后0.83%
GSM8K：RL 后10.77%
训练中 pass@1（400 题）1.5% → 9.5%
平均回答长度（token）262 → 106
两个值得注意的现象。 一是效果立竿见影：d12 的 GSM8K 从 0.83% 到 10.77%，SFT 看 4 遍答案没学会的东西，RL 让它自己试出来了。二是回答变短了，平均从 262 个 token 降到 106 个：模型发现啰嗦不加分，直接调用计算器给答案最划算。RL 优化的是你给的奖励，不是你心里想的目标，这也是它难用的地方。另外这一步很慢，d12 都花了 73 分钟，因为每步要让模型实际生成 256 条回答，是推理的速度而不是训练的速度。

这台机器上遇到的工程问题

  • 语料下载：预训练分片在 HuggingFace 上，镜像站用了一会儿就连不上了。在 ModelScope 找到字节完全一致的镜像（AI-ModelScope/climbmix-400b-shuffle），速度从 3 MB/s 变成 30 MB/s，200 个分片 10 分钟下完。
  • 评测和 SFT 数据集：nanochat 通过 HuggingFace 的 parquet 接口取数，服务器访问不了。在本机按同样的目录结构下载好再同步过去。
  • 评测数据包：26 MB 的文件放在美国的 S3 上，服务器上只有 31 KB/s，训练在第一次 CORE 评测时空等了 19 分钟。
  • FlashAttention 3：加载器要联网校验，离线不认缓存。给 nanochat 加了几行，从本地目录直接加载内核，MFU 从 27% 提到 45%。
  • pip 26 在这个网络下载大文件会挂住，降到 pip 24 并换中科大镜像解决。
