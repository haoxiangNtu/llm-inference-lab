关于 nanochat 的六行。 这是训练实录里自己从零训练的三个模型，各有 SFT 后和强化学习后两个版本，通过一个 OpenAI 兼容的小服务接进同一套脚本。它们跑在单张卡的 nanochat 引擎上，没有批处理，上下文只有 2048，所以只测了单流和并发 4、没有长上下文档，质量测试题量减半，RL 版本只测质量。数字本身不好看，但"自己训的模型和前沿开源模型差多远"从此有了同一口径的答案。
一个修正：第一次测时，那个小服务在工作线程里跑生成，而 nanochat 的计算器靠 SIGALRM 设超时，只能在主线程用。每次调用计算器都悄悄失败，模型拿不到结果就停止作答。RL 版本几乎每一步都调用计算器，受害最重，GSM8K 上 d32-rl 从 4% 变成 20%，d24-rl 从 1% 变成 17%，d12-rl 从 1% 变成 9%；SFT 版本和 HumanEval 修复前后几乎不变。修复后全部重测，下面是修复后的数字。

Qwen3.6 是最"话多"的思考者，HumanEval 有 31 题在预算内没写完代码，JSON 抽取这种简单任务也要先想一千多个 token；GLM 的答案最简洁、质量最高，代价是慢。给思考模型更大预算或关掉思考，分数会明显不同。

测试过程中修正的不公平

  • Qwen3.6-35B-A3B：json/tools 以 2048 token 预算重跑（首轮 512 预算被思考占满）；128K 档超过服务的 max-model-len 131072（实际 149K token）被拒，改测 110K 档
  • Qwen3.8-27B：json/tools 以 2048 token 预算重跑（首轮 512 预算被思考占满）；tools 使用 qwen3_xml 解析器重跑（首轮 hermes 解析器不匹配该模型的 XML 格式）；128K 档超过服务的 max-model-len 131072（实际 149K token）被拒，改测 110K 档
